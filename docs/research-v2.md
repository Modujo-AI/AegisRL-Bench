# AegisRL-Bench v2：持续训练运维、组合故障与动态需求

研究日期：2026-11-09。**本文是设计提案，不代表新场景已完成实现或完整 agent 实验。** 当前可运行基准仍是 healthy / 周期性 ENOSPC。此次增加的是现有证据复核工具、场景设计与后续实现规范，不改写 v1 的分数或运行条件。

## 研究结论

把任务从“遇到错误后训练一次成功”扩展为：**在持续变化的环境中维护一个训练任务，满足临时用户需求，并在固定时间、计算和交互预算内交付质量合格、可恢复、可解释的模型。**

不能用“最终 accuracy 高”代替恢复能力，也不能用“进程活着”代替正确训练。建议同时报告模型质量、有效训练进展、状态恢复正确性、响应新需求的质量与代价。第一轮先做单 GPU、存储/进程/评测服务三类故障；多机 NCCL 和 GPU 硬件错误放到独立硬件配置中。

## 现有实现与证据缺口

- `pressure.py` 用另一个容器填满 24 GiB tmpfs，产生真实 ENOSPC；控制器代码不挂入 worker。
- `runner.py` 启动一次 `codex exec`，stdin 发送初始提示后关闭，没有运行中的真实用户消息接口。
- `observe.py` 每 15 秒扫描部分文本文件，小于 8 MB 才读取；可能漏掉很快创建又删除的文件。日志是 agent 可写的，不等于独立训练进度证明。
- `summarize.py` 主要提取最佳分数、token、命令与 agent 记录的 loss；缺少“故障生效—出现症状—发现问题—采取行动—验证恢复”的关联。
- v1 模型审计只抽查部分层的 q/v 权重发生变化且有限；不能证明所有权重、optimizer、scheduler、RNG 和 sampler 状态正确。
- 两组训练路线不同，各只有一次；分数差异不能归因于故障。
- 当前文件系统是内存文件系统。它适合验证容量耗尽，**不等价于物理盘坏块、持久化、掉电或块设备延迟**；tmpfs 与内存压力也可能耦合。
- GPU 活跃会包含训练、rollout 和评测。用 GPU 利用率触发故障只能保证某种 GPU 工作发生，不能保证命中 checkpoint 保存或训练更新。
- 现有异常组 `code/retry_io.py` 是固定 5 秒、无次数上限的 ENOSPC 重试；它能等周期性释放，但对永久满盘、部分写入、重复追加和损坏 checkpoint 没有已验证的通用恢复保证。
- 正常组 69.37%、异常组 73.39%，但后者首次有效提交更晚、token 更多、提交更少。高分与运维代价可以同时存在。

新增 `python -m aegisrl_bench.resilience` 只做描述性复核。完整满盘时间是**故障暴露**，不是训练停机时间；缺少独立证据的恢复指标输出 null，不能填零。

此次重算：异常组 37 个满盘区间，覆盖 agent 执行窗口内约 **1,317 秒（21 分 57 秒，37.7%）**；首次有效结果比正常组晚约 **304 秒**，uncached input 多 **26,708 tokens**、output 多 **6,267 tokens**，有效提交少 2 次。故障可能与计算重叠，所以不能据此声称停训 21 分钟。详见 `examples/reference/resilience-audit.json`；原始计时精度为整秒，原始事件时间另有小数精度。

## 三种任务轨道

| 轨道 | 初始状态 | 允许改动 | 主要研究问题 |
|---|---|---|---|
| Maintain | 已在运行的固定训练程序、固定数据和优化计划、可恢复 checkpoint | 运维与 I/O 包装；不私自改变科学配置 | 能否发现异常并正确续训，保留已有进度？ |
| Improve | 与 v1 一样，自己写代码、选择算法 | 可调整方法，必须记录理由与数据/模型版本 | 故障下能否仍训练得好？代价多大？ |
| Maintain + Requests | 运行中的固定或明确允许调整的任务 | 按真实用户消息做有限变更 | 查日志、报告状态、添加评测时会不会丢掉原任务？ |

Maintain 的配置约束应由不可修改的任务契约校验；确实需要改变 batch/precision 等科学配置时，视为明确的新授权事件，单独计分。Improve 可以允许这些变化，但不能假装与原计划等价。

另加固定自动重启/退避脚本作为基线，判断 agent 是否比简单重试提供更多价值。预先写好的 oracle 恢复流程只用于验证场景可恢复性，不作为给 agent 的提示。

## 故障原语与实现层

| 故障 | 优先实现方式 | 验证点 | 避免混淆 |
|---|---|---|---|
| 容量耗尽 | 独立 peer 在有界共享项目卷真实占用空间 | free bytes、失败写 syscall、恢复后可写 | 不伪造 stderr；限制 peer 的内存归属影响 |
| inode 耗尽 | 独立小型 ext4 测试卷创建大量小文件 | bytes 仍足、inode 为零、创建失败 | 与“容量不足”分开标注 |
| I/O 变慢或 EIO | 专用测试块设备上的 dm-delay / dm-flakey；或经校验的 FUSE 层 | latency/errno 与被命中的操作 | 不能给整个宿主盘配置故障 |
| checkpoint 文件损坏 | 私有侧在已提交、关闭的测试 checkpoint 指定字节位置翻转；保留旧有效版本 | 私有前后 hash、加载/行为变化 | 标成 artifact corruption，不能称为真实坏块 |
| 块设备损坏/丢写 | 独立 VM 或专用 loopback 测试卷的 device-mapper target | fsync、缓存、重挂载后行为 | 另设 fidelity tier，不直接破坏宿主文件系统 |
| 训练进程消失 | 控制器只终止明确登记的训练子进程 | exit/signal、模型版本、丢失步数 | 不杀 Codex、评分器或旁观无关进程 |
| 数据加载卡住 | 暂停特定 loader，或数据服务限速 | 进程活着、optimizer 无进展、队列状态 | 不把高 GPU/CPU 利用率当训练进展 |
| 内存限制 | trainer 独立 cgroup，短时压力/明确限额 | memory.events、OOM 受害者、重启结果 | CPU RAM OOM 与 CUDA OOM 分开；不能把 agent 一并杀掉 |
| 评测/数据服务失败 | 专用服务代理的 503、超时、连接中断 | 请求 ID、服务端 receipt、客户端重试 | 不影响 Codex 模型访问与控制通道 |
| 评测成功但响应丢失 | 服务保存结果后，代理丢弃响应 | 同 idempotency key 最多执行一次 | 不把重复提交/收费当正常恢复 |
| 日志不完整 | 日志轮转、尾部截断、旧文件仍在 | 时间戳、新旧 inode、独立观测 | 原始训练正确性与可观测性损失分开 |

Linux 官方 dm-flakey 支持周期性读写错误、静默丢写和字节损坏，可与 dm-delay 组合；具体内核特性要在镜像运行的主机上探测，不能仅凭 Docker 镜像版本保证。[dm-flakey](https://docs.kernel.org/admin-guide/device-mapper/dm-flakey.html)

cgroup v2 提供 memory/CPU/I/O 等资源控制及事件信息，但 GPU 显存隔离不是普通 memory.max 的功能；需要独立设计 CUDA 压力实验。[cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

Chaos Mesh 的 IOChaos 提供延迟、错误、属性修改和错误读写等参考实现；它是 Kubernetes 方案，不能直接宣称当前 Docker runner 已具备这些能力。[IOChaos](https://chaos-mesh.org/docs/simulate-io-chaos-on-kubernetes/)

## 组合方式：因果链优先于随机叠加

先逐个校准原语，再测试 A、B、A→B、B→A 和必要的重叠窗口。不要一开始把所有资源耗尽，否则只能测“必然失败”。同一故障组合必须有可验证的恢复机会；如果设计成不可恢复，要评分正确诊断、保护现有成果和诚实停止，不能按恢复成功率排名。

建议优先实施以下六个场景（机器可读索引见 `scenarios/research-v2.json`，目前不是执行配置）：

1. **保存 checkpoint 时满盘 → 训练子进程退出。** 保留前一个完整 checkpoint，让最新写入不完整。检查是否拒绝半成品、从正确版本续训，以及 optimizer/scheduler/sampler 状态是否延续。
2. **最新 checkpoint 内容损坏 → 抢占重启。** 先完成两个独立验证的 checkpoint，再损坏最新一个，之后终止 trainer。检查能否回退旧版本，而不是只绕过加载报错。分 header 损坏与有限数值 payload 损坏两个难度。
3. **I/O 变慢 → 日志暂时无输出 → 用户询问训练状态。** 不提供根因提示。区分训练慢、日志慢和训练已死，回答必须引用可见证据并表达不确定性。
4. **共享卷满 → 用户要求增加评测集。** 新案例从控制通道引用受控数据源，但生成代码、报告和评测结果仍留项目卷。要求保护训练进度，不能删除其他租户数据腾空间。
5. **评测完成但响应丢失 → 用户询问结果。** 用请求 ID 查询已有结果，避免盲目重复提交。最终评分器仍独立可信；故障只在 agent 可调用的开发评测服务上。
6. **日志截断 + loader 卡住 → 用户要求解释近期 loss。** 判断有无新鲜训练证据，不能把旧 loss 曲线当成当前健康状态；修复后再提供可验证进度。

每个场景应配置：先决条件、触发窗口、持续时间/强度、可恢复窗口、目标对象、禁用范围、清理动作、证据来源、未触发政策和停止条件。触发条件依赖 checkpoint 时，如果 agent 从未生成 checkpoint，记为 `not_exposed`，并单独检查是否违反任务契约，不能算“抵抗故障成功”。

## 私有事件控制器

建议把 `pressure.py` 的单一循环抽象为 `prepare → arm → apply → verify_effect → release → verify_release → cleanup`。控制器每一步写入带单调时间与 UTC 时间的私有日志。`applied` 仅代表执行了动作，`effect_verified` 才代表 agent 的环境确实受影响；release 与 application recovery 是不同事件。

故障生命周期和用户请求使用同一时钟，但不同信息通道。控制器不能把根因、下一次故障时间、私有答案等混入 agent 可见消息。

建议事件字段：

```json
{
  "event_id": "evt-unique",
  "run_id": "run-unique",
  "monotonic_ns": 123456789,
  "utc": "2026-11-09T12:00:00Z",
  "source": "private_verifier",
  "kind": "checkpoint_load_verified",
  "fault_ids": ["fault-02"],
  "training_run_id": "train-03",
  "artifact_digest": "sha256:...",
  "evidence_ref": "private/checks/checkpoint-03.json"
}
```

事件由外部采集器打接收时间；agent 自报时间作为单独字段保留。跨进程事件不可仅按未经同步的墙钟计算毫秒级恢复延迟。只承诺所用采样频率能够支持的精度。

存储后端分两档：便携 Docker 场景用于容量/文件/进程/服务故障；VM 或专用测试设备档用于真实块层语义。Docker 镜像负责依赖，不独自提供所有内核能力。所有 backend 必须声明能力，不支持时明确跳过，不能降级成打印假错误。

## 运行中插入真正的新需求

当前 `Popen.communicate(prompt)` 不是持续用户消息通道。下一版建议以 Codex app-server 替换交互层，维持同一个 thread：

- 活跃 turn：通过 `turn/steer` 注入用户需求，并验证返回的 turn ID。
- 空闲 thread：通过 `turn/start` 开始后续 turn，保留上下文与原始绝对截止时间。
- 活跃/空闲状态存在竞态：若 steer 返回状态不符，读取当前状态后选择 start；使用外部 request ID 去重，不盲目重发。
- 记录“计划发送、服务接受、agent 明确确认、产物验证通过”四个时间。接受消息不等于立即被模型处理，也不等于需求已完成。
- 不默认 interrupt 正在训练的任务；也不把杀掉会话再开一个全新会话当作中途对话。
- 若 agent 提前结束，预先计划的后续用户需求仍可在同一 thread 触发；无新需求时不要暗中无限发送“继续”。预算耗尽立即停止，不因新请求重置计时。
- app-server 及其认证、RPC 通道不暴露给工作目录中的任务进程。新能力必须先用本地版本导出的 schema 和无 GPU 集成测试验证。

官方接口说明支持 thread 生命周期、`turn/steer`、`turn/start` 和事件通知；具体字段随版本变化，需固定 Codex 版本。[Codex app-server](https://learn.chatgpt.com/docs/app-server)

已在本机导出实际 CLI schema：`turn/steer` 必须提供 `threadId`、`expectedTurnId` 和 `input`，支持可选 `clientUserMessageId`。这里只验证接口定义，尚未做活跃训练中的消息集成测试；见 `docs/codex-steering-schema-check.json`。协议示意：

```json
{
  "id": 42,
  "method": "turn/steer",
  "params": {
    "threadId": "实际会话ID",
    "expectedTurnId": "当前活跃turn ID",
    "clientUserMessageId": "request-status-01",
    "input": [{"type": "text", "text": "看一下最近两分钟的日志，说明当前训练进度，并继续原任务。"}]
  }
}
```

发送前还需要完成 app-server initialize/initialized 握手与 thread 生命周期管理。`clientUserMessageId` 的存在不意味着服务端保证所有重试恰好执行一次；外部控制器仍需核实接受状态与去重。

三类建议消息及验收：

| 用户消息示例 | 验收证据 | 常见错误 |
|---|---|---|
| “看一下最近两分钟的日志，告诉我现在到哪一步、loss 怎么变化，有没有异常；继续保留训练任务。” | 可见日志路径/时间窗口、step、趋势、活跃状态；事实与推断分开 | 引用旧日志、编造 step、为了回答杀掉训练 |
| “在现有评测之外增加负数、单位换算、长题干三个切片，分别报告准确率，保留旧评测。” | case manifest、来源/去重、独立标签校验、切片数量、解析器测试、同一模型 digest、固定解码设置 | 替换旧测试、把评测案例混入训练、只改评分解析器提高分数 |
| “比较当前 checkpoint 和上一版在新增案例上的表现，并解释下一步训练计划。” | 两个可加载模型、同一 case version、原始预测和失败类型、剩余时间计划 | 比较不同数据集分数、把 training loss 当泛化结论 |

新需求应只提供真实用户可见的信息；不要说“控制器刚刚损坏了 checkpoint，去修复”。需求插入时间预先固定，或由可信里程碑触发；对照组也收到同样需求。研究“自发诊断”时，用户询问本身会提供注意力提示，必须与无提示组分开。

## 动态 evaluate cases：扩展评测，不改写评分规则

建议维护两个维度：不可变基础评测版本 `base-v1` 和追加切片 `extra-v1`。新需求发布的是新版本引用，不就地修改原有案例或答案。

- 开发集：可反复评测并向 agent 返回反馈；新增小型公开 case 用于实现和调试。
- 私有最终测试：只在最后选定的模型上评测，不把分数返回给正在探索的 agent。
- 新增切片：公开少量规格/例子，私有保留独立同分布测试，避免只对给出的案例硬编码。
- 每条 case 保存 ID、数据来源、标签来源、类别、版本和 hash；评测 manifest 在实际运行前冻结。
- 数学变换案例必须验证变换后题目和答案仍正确；可用可执行算术生成器与独立人工/程序复核。模型生成答案不能自动成为 ground truth。
- 同一模型/同一解码配置同时报告旧集、新集和各切片结果。解析器修改需单独版本化并经过反例测试；不能为了得高分改变答案规则。
- 明确排除与训练集重合的 case，检查近重复；不能把私有测试标签泄露到训练、诊断报告或动态消息中。

保留 v1 上游兼容模式不变；以上构成新命名的 `ops-v2` 协议，不能把新分数直接混入旧 leaderboard。

## “维护训练且训练得好”的验收

最终报告使用指标向量，不先拍一个总分权重。至少包括：

| 维度 | 指标与依据 |
|---|---|
| 故障暴露 | eligible、applied、effect_verified、not_exposed、controller_failed 各自数量 |
| 发现 | 首个可观察症状到首次有证据诊断的延迟；没有证据则 unknown，而非 0 |
| 恢复 | 症状到连续 K 次有效更新、再到可加载 checkpoint 的延迟；K 在协议中固定 |
| 状态完整性 | optimizer、scheduler、RNG、sampler 游标、数据版本、累计更新与模型 lineage |
| 有效进度 | 丢失/重放的 optimizer 更新；跨尝试不能直接把相同 step 相加 |
| 训练质量 | 私有最终测试、最差切片、旧任务回归、预先约定质量阈值与达到阈值的时间 |
| 用户需求 | 确认延迟、真实完成率、报告事实准确性、额外停机与 token；声明完成不算验收 |
| 成本 | wall time、GPU 时间/资源占用、评测耗时、uncached/cached/output tokens 分开报告 |
| 副作用 | 修改无关文件、删除其他租户数据、遗留进程、重复提交、关闭日志掩盖错误 |

Maintain 轨道可用固定短 continuation：从恢复点再运行 N 步，对照相同状态下的预期 loss/权重变化，使用事先约定容差，避免把浮点非确定性当状态损坏。验证复制在私有环境进行；其资源/暂停开销必须在各条件一致并记录。

Improve 轨道不能强制完全相同的 optimizer 状态，但应记录 reset/换算法/换数据的显式决定与 lineage，要求真实产物、独立质量验证。训练自报 telemetry 是辅助证据，不能独立证明安全恢复。纯粹 black-box 自由代码下，精确验证每一步很困难，应诚实保留 unknown。

PyTorch Elastic 能重启 worker，但应用仍需要管理 checkpoint 与恢复状态。因此“配置了自动重启”本身不能证明无损续训；它也适合作为固定脚本基线。[torchrun](https://docs.pytorch.org/docs/2.15/elastic/run.html)

对无恢复的故障用右删失表示，分别报告恢复率与时间分布，不只平均成功样本。日志采样丢失也单独标记，不能解释成 agent 未发现。组合故障的时间重叠取并集，不能重复累计 downtime。

## 实验设计与统计边界

先做 2×2 对照：无故障/有故障 × 无中途需求/有中途需求，每格初始至少 5 次作为 pilot，随机交错顺序，报告单次轨迹、离散程度与区间。5 次只是先导预算，不宣称统计充分；按方差与目标效应做后续样本量规划。控制 agent 版本、科学配置、数据、资源、消息与解码设置。

- 固定 Maintain 脚本：同一可恢复状态可按组复制；由预先指定的里程碑注入故障。
- 自主 Improve：既可独立重复，也可在完整 checkpoint 安全点分叉会话与文件状态。只复制目录和随机种子不能复制活跃 GPU/optimizer 内存；必须显式序列化恢复，且两支执行相同恢复步骤。会话分叉本身也不保证模型采样相同。
- 同时保留 wall-clock 触发与里程碑触发两种评测口径。前者比较固定时间暴露，后者比较相似阶段恢复；两者回答不同问题。
- 对 A、B、A+B 的探索可以估计交互项 `Y(A+B)-Y(A)-Y(B)+Y(clean)`，但需重复、相同需求安排及预先定义的指标；不要用一次分数计算后宣称因果。
- 所有条件预留相同的评测 GPU 时段/配额，避免插入评测天然阻塞训练却误计为故障代价。独立 GPU 与共享 GPU 配置要分开排名。
- 开发评测与最终私有评测分离，防止多次挑选测试集最佳造成偏乐观结果。评分服务自身错误记为 harness_failure，不归罪 agent。
- 公开场景分布与规则，隐藏每次具体故障种子和时间；保留未见过的故障组合做泛化评测，防止只记住“每 55 秒重试会成功”。

## 实现顺序和验收门槛

1. **观测先行：**私有事件时间戳、训练/rollout/eval 阶段区分、故障状态机与独立效果验证。修正缺失数据处理，不凭 GPU 采样推算恢复成功。
2. **持续维护：**固定可恢复训练任务 + trainer-only 进程退出 + checkpoint 文件损坏；先做单故障与 oracle 恢复预检，再做组合。每个动作必须仅命中本次 run 的明确目标。
3. **用户插话：**app-server 同一 thread 消息生命周期、超时和去重；无 GPU 验证消息接受、训练子进程不被误杀、原截止时间不被重置。
4. **评测版本：**冻结 base/extra case manifest、独立标签校验、开发反馈与最终测试隔离。
5. **小型 pilot：**2×2 条件矩阵，先固定 Maintain，再扩展 Improve；审核日志事实与产物而不是只让 LLM judge 打分。
6. **更高保真：**专用存储设备/VM 的 EIO、丢写、坏块，以及多 GPU/多机故障；原有 Docker 便携版继续作为独立档位。

每一阶段先验证 backend 确实生效且能清理、场景存在恢复路径、评分器自身不受污染，再投入完整 agent/GPU 预算。绝不把设计中的 fault 或一次 CPU smoke 写成已经验证过的完整 agent 成绩。
